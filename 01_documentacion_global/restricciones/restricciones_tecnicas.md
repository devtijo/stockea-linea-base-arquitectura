
| Tipo                | Categoria                  | Restricción técnica                                                                                                                                                                        | Justificación                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Propia del proyecto | Prácticas de diseño        | El diseño y desarrollo del software debe seguir los principios SOLID en todas las capas de la aplicación.                                                                                  | Aplicar los principios SOLID en el desarrollo de STOCKEA permite construir un software mantenible, extensible y con bajo acoplamiento, lo que resulta indispensable para un producto que debe evolucionar continuamente incorporando nuevos módulos y ajustándose a las necesidades de distintos tipos de negocios perecederos sin generar deuda técnica que frene su crecimiento.                     |
| Propia del proyecto | Prácticas de diseño        | El sistema debe implementarse bajo arquitectura hexagonal, con separación estricta entre dominio, aplicación e infraestructura.                                                            | La arquitectura hexagonal aísla la lógica de negocio de los detalles técnicos, permitiendo reemplazar la base de datos, el framework web o los proveedores externos sin reescribir el motor de recomendaciones ni los cálculos de inventario, que son el diferenciador central del producto.                                                                                                           |
| Propia del proyecto | Prácticas de diseño        | El sistema debe adoptar el enfoque offline-first como principio de diseño transversal en el frontend.                                                                                      | La promesa central del producto frente a competidores es la operación completa sin conexión a internet en zonas de conectividad intermitente. Diseñar con un enfoque offline-first desde el inicio evita retrabajos costosos, garantiza que la experiencia de usuario sea consistente independientemente del estado de red y establece las bases para la sincronización posterior con el servidor.     |
| Propia del proyecto | Patrones de diseño         | El sistema debe aplicar patrones de diseño GRASP y los principios DRY y KISS a lo largo del código base.                                                                                   | La adopción de estos patrones y principios mejora la calidad del software y facilita su mantenimiento a lo largo del tiempo. GRASP guía la asignación clara de responsabilidades en clases y objetos, DRY evita duplicación innecesaria de lógica y KISS mantiene el diseño simple y comprensible. En conjunto, estas prácticas producen un código más legible, mantenible y menos propenso a errores. |
| Propia del proyecto | Patrones de diseño         | El sistema debe implementar el patrón puerto-adaptador para todas las integraciones con servicios externos (mensajería, correo, facturación electrónica).                                  | Los proveedores externos evolucionan y cambian sus términos comerciales con el tiempo; un acoplamiento directo con un proveedor específico obliga a modificar código de negocio cuando se cambia de proveedor. El patrón puerto-adaptador permite intercambiar proveedores mediante configuración externa sin afectar el dominio, protegiendo la inversión en la lógica del sistema.                   |
| Propia del proyecto | Prácticas de código limpio | El desarrollo debe seguir prácticas de código limpio (Clean Code), evitando Messy Code y Code Smells.                                                                                      | Aplicar prácticas de código limpio facilita la comprensión del código, mejora la legibilidad y reduce la probabilidad de introducir errores al asignar nombres descriptivos a variables, métodos y clases. En un producto SaaS multi-tenant que debe soportar mantenimiento continuo, un código limpio es la base para escalar el equipo de desarrollo sin degradar la calidad.                        |
| Propia del proyecto | Prácticas de desarrollo    | El desarrollo debe aplicar Test-Driven Development (TDD) obligatorio en los servicios del dominio (motor de recomendaciones, cálculo de vencimientos, integridad transaccional de ventas). | El núcleo del dominio implementa las reglas de negocio que dan valor al producto; un error en estos cálculos destruye la confianza del cliente y es la principal fuente potencial de rechazo del sistema. TDD garantiza cobertura del 100% en estos servicios críticos y permite refactorizar con seguridad ante cambios futuros.                                                                      |
| Propia del proyecto | Prácticas DevOps           | El desarrollo debe adoptar prácticas DevOps con pipelines de integración y despliegue continuo automatizados.                                                                              | Las prácticas DevOps garantizan la entrega continua, la eficiencia operativa y la confiabilidad del sistema. La automatización de pruebas, despliegues y monitoreo agiliza el ciclo de vida del software, permite una respuesta rápida a los cambios del mercado y minimiza tiempos de inactividad, lo que resulta crítico para cumplir con los SLA comprometidos con los clientes suscriptores.       |
| Propia del proyecto | Prácticas DevOps           | Los despliegues a producción deben realizarse sin tiempo de indisponibilidad mediante estrategias de migración de base de datos compatibles hacia adelante y hacia atrás.                  | El SLA comercial comprometido con clientes del plan Enterprise no permite ventanas de mantenimiento programadas; una migración que exija indisponibilidad rompe el contrato de servicio y erosiona la confianza. El patrón expand-contract en migraciones permite evolucionar el esquema de base de datos sin interrumpir el servicio activo.                                                          |
| Propia del proyecto | Seguridad                  | El sistema debe adoptar el enfoque de seguridad en profundidad (defense in depth) con validaciones en cliente, servidor y base de datos.                                                   | Confiar exclusivamente en una única capa de validación deja al sistema expuesto ante manipulación del cliente desde herramientas del navegador o peticiones directas al API. La seguridad en profundidad garantiza que aunque una capa falle, las siguientes contengan el impacto y protejan la integridad de los datos del negocio.                                                                   |
| Propia del proyecto | Seguridad                  | El sistema debe implementar aislamiento estricto multi-tenant a nivel de aplicación y de base de datos, con filtros automáticos por identificador de negocio en todas las consultas.       | El aislamiento entre negocios es una restricción no negociable del producto; una consulta sin filtro de tenant que exponga datos entre negocios sería una brecha de seguridad irrecuperable en el mercado y generaría incumplimiento directo de la Ley 1581 de Habeas Data.                                                                                                                            |
| Propia del proyecto | Integridad de datos        | Los cálculos monetarios y porcentuales del sistema deben implementarse con tipos decimales de precisión fija , nunca con punto flotante nativo.                                            | Los tipos float y double introducen errores de redondeo que en operaciones financieras acumuladas generan descuadres de caja imposibles de rastrear y destruyen la confianza en el sistema.                                                                                                                                                                                                            |
| Propia del proyecto | Integridad de datos        | Los registros de auditoría (ventas registradas, ajustes de inventario, aperturas de caja, cambios de precio) deben ser inmutables tanto a nivel de aplicación como de base de datos.       | La trazabilidad legal exigida por el Código de Comercio de Colombia y la confianza del cliente en el sistema dependen de que ningún usuario, incluido el administrador, pueda alterar registros históricos. Las correcciones deben modelarse como nuevos registros que referencian al original.                                                                                                        |
